# N05-00　时间戳与延迟口径（T0~T5）——替代"135 秒物理实测下限"

> 对应审核：Commit 0338a5d 审核稿 §3 P0-06、§5 N05。日期：2026-10-29。
> 关联代码：`02_源代码与配置/source/server.py`（`batch_recv_lag_stats()`，原 `lag_stats`）、
> `influx_source.py`（`recv_ts` 打点）。产生关系：本文件解释这两处代码输出的口径。

## 1. 六段独立时钟定义

| 记号 | 事件 | 本链路能否打点 | 打点位置 / 不能打的原因 |
|---|---|---|---|
| **T0** | 物理崩刃发生的时刻 | ❌ 不可测 | 需独立高速传感（振动/声发射）或事后实物比对；现有 FOCAS 数据无任何物理事件标记 |
| **T1** | 机床侧数据生成时刻 | ✅ | 采集盒写入 Influx 的 `_time`（代码：`influx_source.py` 的 `ts` 字段） |
| **T2** | 采集盒 → InfluxDB 写入完成时刻 | ❌ 盲区 | 需采集盒侧或 Influx 服务端打点；InfluxDB 2.x 默认不暴露逐点到达时间 |
| **T3** | 应用查询拉取到数据 | ≈T4' | 本架构里拉取即落库，无独立打点 |
| **T4'** | 应用批量落库时刻 | ✅ | `recv_ts`（**批打点**：同一次拉取的所有行共用一个值；加列于 2026-10-29，R06 P0-a） |
| **T5** | 机床实际停止时刻 | ❌ 不存在 | 无报警/停机接口（`server.py` 全文无 FOCAS 写），策略为 MONITOR_ONLY + `SAFETY_PERMIT=False` |

## 2. 各延迟量的严格口径

| 量 | 定义 | 代码来源 | 语义边界 |
|---|---|---|---|
| 批次接收延迟 | T4' − T1 的上界 | `batch_recv_lag_stats()`（原 `lag_stats`，因容易被读成端到端物理延迟而改名，审核 P0-06） | 含 Influx 查询+网络+解析；**不是** L2 物理入库时延 |
| 轮询等待 | 0 ~ POLL_SEC(15 s)，均值约 7.5 s | `influx_source.py: POLL_SEC` | 周期不是每事件必等满 15 s |
| 封口等待 | 0 ~ SEAL_DELAY_SEC(120 s) | `server.py: SEAL_DELAY_SEC` | 是"件收齐判定"的策略超时，**不是**从 T0 起算的检测时长 |
| 等待预算近似 | 轮询 + 封口 ≈ 135 s | 上两行之和 | **仅为本链路特定情况下的等待预算之一**，禁止写成"现场实测下限/物理下限" |

## 3. 盲区计数（审核要求"保留跨日迟到或时钟异常的盲区计数"）

`batch_recv_lag_stats()` 返回字段：

| 字段 | 含义 |
|---|---|
| `n` | 参与统计的行数（recv_ts 非空、0 ≤ lag ≤ 86400 s） |
| `neg` | 负值条数（机床/服务器时钟不同步线索，应趋近 0；不为 0 时先查时钟再谈延迟） |
| `stale` | >1 天条数（停机跨天迟到，不计入延迟分布但**不静默丢弃**） |
| `n_no_recvts` | `recv_ts IS NULL` 的老行总数（加列迁移前的盲区行数） |
| `note` | 口径自述（"T1→T4' 上界，不是 L2 物理入库时延"） |

## 4. 端到端"崩刃→停机"时长为什么现在不可测

完整链路应为 T0→T5。本项目当前：T0 无标记、T5 无接口，**两端都不可观测**，
所以任何"X 秒检出"的表述都只能限定在 T1→T4' 或等待预算层面。
若要做审核 §3 P0-06 要求的独立时钟实测（最大/最小/分位/缺失值），前提是：
① 引入与机床时钟同步（或标注偏移）的独立打点；② 存在真实的报警/停机输出通道。
两者目前均不具备 → 相应字段如实报 `UNKNOWN`，不臆造数值。
