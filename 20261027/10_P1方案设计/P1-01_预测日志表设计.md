# P1-01 在线预测日志表设计

> 状态：**设计，未落库**。DDL 见 `02_源代码与配置/schema/predictions_DDL_proposed.sql`。
> 核心约束：**事后历史回放不得冒充前瞻性日志。**

---

## 一、为什么必须有这张表

没有它，就永远无法回答"当时预测了什么"。本轮所有预测（57 条）都是**事后回放**——用 2026-10 的数据算出 2026-09 的"预测"，虽然严格做了时间截断，但**没有留存当时的预言**，因此不满足任务书第十二节第 2/3 条。

---

## 二、表结构要点（不是全字段罗列，只说关键设计）

| 字段 | 为什么必须有 |
|---|---|
| `ts_predict` | 真实推理时刻。**这一列是"前瞻"与"回放"的唯一物理分界** |
| `is_replay` | 0=当时真实推理；1=事后回放。**默认 0，回放必须显式置 1** |
| `data_watermark` | 输入数据的截止时刻。没有它，无法证明"没用未来数据" |
| `physical_life_id` | 物理刃口。用户已确认不翻刃 → 1 周期 = 1 刃口 |
| `tool_age_pieces` + `tool_age_source` | 刀龄及来源（event/cold/UNKNOWN）。`cold` 时刀龄只是下限 |
| `model_version` + `feature_version` | 版本不一致的预测不可混在一起评估 |
| `rul_point / rul_lo / rul_hi / pi_level` | 点值与区间，分开存 |
| `calibrated` | 0=探索性区间（本轮全部为此）；1=经过覆盖率校准 |
| `quality_grade` | 预测当时的 A/B/C/D，用于事后分层 |
| `actual_end_ts / actual_life / actual_label / label_quality` | 后验回填。**允许长期为空**（右删失） |

---

## 三、写入时机（三个必须写、一个不许写）

| 时机 | 写什么 |
|---|---|
| 每次跨过复核点 b/h/M0 | 写一条预测（含当时刀龄、区间） |
| 每天固定一次（有在切削） | 写一条"当前状态"预测，用于覆盖率统计 |
| 换刀事件发生时 | **回填**上一条预测的 `actual_*` |
| ❌ 禁止 | 用离线 CSV 批量回放后写进同一张表而不置 `is_replay=1` |

---

## 四、与现有表的关系

```text
pieces(allnum)  ──┐
                  ├──> predictions(physical_life_id, tool_age_pieces)
tool_events      ──┤        │
(换刀/新刀/刀废)   │        └──> 回填 actual_end_ts / actual_life
history(life)   ──┘
```

**不新建第二套刀龄计数**：`tool_age_pieces` 直接取 `COUNT(pieces WHERE prog=? AND allnum>base_allnum)`，与本轮审计口径一致。

---

## 五、表能回答的问题（也是它存在的理由）

1. 某把刀在第 40 件时，系统当时说还剩多少？区间多宽？
2. 这个预测是在换刀之前多久做出的？
3. 同一把刀在不同时点的预测是否自相矛盾？
4. 区间覆盖率到底是 56% 还是 80%？
5. 换刀后，`actual_life` 与当时的 `rul_point` 差多少？

**这是唯一能证明"这不是事后诸葛亮"的机制。**
