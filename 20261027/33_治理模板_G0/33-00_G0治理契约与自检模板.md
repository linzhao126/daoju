## 0　这份文件解决什么问题

审核方说「每轮必须自检」，但如果自检全靠自觉，下一轮还会犯同样的错。
> ⛔ **事故复盘（4 次同类违规，均已撤回）**：`16-00` 曾写"它们不是两种失效机制"、`14-00` 曾写"其余方向已被证否"、`17-00` 曾写"当前唯一站得住的方案"、`s31` 曾写"必然预防性更换"。这四条现已在各自文档中标注撤回。

**所以本文件做三件事**：

1. 把 G0-01~05 转成**可勾选的自检表**（不是抄原文）；
2. 建**红线词表**（`g0_redlines.csv`）——把"哪些话不能说"变成可直接 grep 的清单；
3. 给一个**扫描脚本**（`check_g0.py`）——对任何一份 md 报告做机械检查，输出 PASS/WARN/FAIL。

> **核心原则**：治理不能靠"我保证"，要靠"能被别人一条命令查出来"。

## 2　G0-02　RUL 必须按 C0/C1/C2/C3 分级

### 2.1 四级定义（**每个 RUL 结论必须标级，不标即视为违规**）

| 级 | 是什么 | **不是什么** |
|---|---|---|
| **C0** | 采集、显示、加工计数、换刀登记、数据质量管理 | **不是 RUL 预测** |
| **C1** | 历史寿命中位数 / 固定阈值 / 人工换刀策略 | 是经验统计，**不是已验收的个体化 RUL** |
| **C2** | 条件生存、剩余人工换刀件数的**统计预测** | 标签是"距下一次记录换刀"，**不能冒称预测了物理/工艺可用终点** |
| **C3** | 用当前刀具截至预测时刻的 **FOCAS 信号 + 工况特征**，推断其后续可用切削能力 | 这是**核心攻关目标**；标签不支持时必须写"**未能验证/受标签限制**"，**既不能写"C3 已实现"，也不能写"理论上不可能"** |

### 2.2 四个量必须分开（G0-02 原文点名的）

```
机床累计件号  allnum（12 把刀共享）
   ≠ 刀具实际调用次数  ToolUseCount
   ≠ 有效切削段数      AlignedValidPieceCount
   ≠ 等效磨损暴露量    Exposure_mm（Σ X 扫掠跨度）
```

**上一轮的实际教训**：`15-00 §4.1` 曾把 `allnum` 当作 T1111 的件计数器（因为过滤后的 CSV 里它逐个 +1），后来用 3.3 GB 全刀数据才发现 12 把刀共享同一序列。**这就是"四量混用"的典型事故。**

### 2.3 其他硬约束

| # | 约束 | 常见违规 |
|---|---|---|
| 1 | 同一物理刀具跨主程序**不能重置刀龄** | 按 `prog` 分组时把同一把刀算成两把 |
| 2 | 同一主程序**可能多次调用**目标刀具 | 用 `prog` 当唯一键 |
| 3 | 机床寿命计数被人工续设**不是换刀** | 用 `allnum` 跳变当换刀 |
| 4 | 换班/停机/采集缺口可存在，但**不得把恢复采集的第一件视为新刀** | 用"数据重新出现"切件 |
| 5 | **不得把缺失的真实使用量填成零** | 缺件周期直接当 0 件参与统计 |

### 2.4 自检项

- [ ] 每个 RUL 结论都带 `[C0]` / `[C1]` / `[C2]` / `[C3]` 标注
- [ ] 没有把 C2 的"距下次换刀件数"写成"剩余物理寿命"
- [ ] C3 状态只有三种写法：`已实现且经验证` / `未能验证（受标签限制）` / `未开始`
- [ ] 件数口径写明是四个量中的哪一个

## 3　G0-03　崩刃 A 不得偷换为"发现换刀"

### 3.1 四个时刻必须分开

```
T1 物理崩刃时刻      ← 通常拿不到（操作员看不到）
T2 第一件异常加工件  ← 可从质检/返工记录推
T3 人工发现时刻      ← 操作员发现不良品
T4 人工登记/换刀时刻  ← 台账 EndTime
```

**车间实况**：操作员可能在崩刃后又加工多件，直到发现不良品才换刀。**所以 `T4 − T1` 可能是几小时甚至几天。**

### 3.2 三条禁止的替换

| # | 禁止 | 正确做法 |
|---|---|---|
| 1 | 用"破损生命周期中曾报警"当**发生检出率** | 必须报"事件级召回 + 误报密度 + 检出延迟" |
| 2 | 用"换刀前有负载变化"当**崩刃因果检测** | 必须区分正常切削/正常磨损/程序切换/刀补变化下的误报 |
| 3 | 把"1 秒"当成**已完成性能** | 必须给端到端时间戳：采样→轮询→到达→推理→下发→停机 |

### 3.3 做不到时该怎么写（这是 G0-03 第 3、4 条的要求）

**不能**写"所以 A 不做了"，也**不能**自动降级为"每件完成后提醒"。必须给：

```
实测瓶颈 → 候选方案 → 代价 → 请 0 号位裁决的最小问题
```

**本项目当前的实测瓶颈**（`R06 §项目二`）：

| 段 | 状态 |
|---|---|
| 采样（采集盒） | 16 ms（已知） |
| **数据到达 L2** | **完全未知**（库里只有 `_time`，无 `recv_ts`） |
| 平台轮询 | **15 s**（已知，单这一段就超 1 秒目标 15 倍） |
| 封口聚合 | 120 s |
| 推理 | 未测 |
| 下发/停机 | 接口未授权 |

### 3.4 自检项

- [ ] 报"检出"时，说明是 T1/T2/T3 中哪一个的检出
- [ ] 没有把"换刀前负载变化"写成"崩刃检测"
- [ ] 谈 1 秒时给的是**分段延迟表**，不是一个总数
- [ ] 没有出现"因此改成每件后报警"这类自动降级

## 5　G0-05　七项强制自检 + 六步异议

### 5.1 七项自检（**每份回执必须含这一节，缺一项即视为回执不完整**）

| # | 检查项 | 填写要求 | 常见敷衍写法（**不合格**） |
|---|---|---|---|
| 1 | 本轮涉及哪个项目 | RUL / 崩刃A / 崩刃B，分节写 | "涉及刀具寿命项目" |
| 2 | 对应哪项业务目标 | 引用 G0-01~04 的具体条款号 + 说明是"基础能力/实验验证/交付验收" | "为了提升预测精度" |
| 3 | **实际证明了什么** | 预测对象、截止时点、输入、标签真值、样本规模、已跑测试、已证实结果 | "效果良好" |
| 4 | **没有证明什么** | 样本外推边界、弱标签、缺采、未跑测试、真实事件时刻、1 秒时延 | 空着，或只写一句"仍有不足" |
| 5 | 是否改变目标或技术边界 | **默认"否"**；如需变更，写"变更建议，待 0 号位裁决"，**不得先执行后报备** | 悄悄改了目标不声明 |
| 6 | 现有方案能否继续推进 | 分三类：可立即做 / 需补现场数据 / 必须工程试验 | "视情况而定" |
| 7 | 提交可复现证据 | 固定 Commit、文件清单、数据版本与 SHA256、脚本命令、逐刀结果、测试日志、未解决问题 | 只给结论不给脚本 |

> **第 4 项是最容易被跳过、也是审核方最先看的。** 上一轮 `R06` 我写了 14 条"没证明什么"，审核方没有再挑这一项。

### 5.2 六步异议程序（提不同意见的唯一合规格式）

```
① 当前目标        ← 引用 G0-01 原文，不改写
② 受阻证据        ← 数字 + 出处 + 可复算
③ 已试方法及失败范围  ← 试了什么、在什么条件下失败、失败到什么程度
④ 可执行替代方案   ← 至少一个，带预期效果
⑤ 预计收益/代价/风险
⑥ 需要 0 号位裁决的最小问题  ← 一句话，可回答"是/否"
```

**红线**：裁决前**维持既定目标**，保留负结果和异议记录，**不能以"AI 认为不可行"为由收缩项目**。

### 5.3 自检项

- [ ] 回执里有独立的《项目目标遵循性检查》小节
- [ ] 七项齐全，且第 4 项不是空话

## 7　怎么用（三步）

### 7.1 写报告时

复制 `33-01_R06遵循性检查_模板.md`，逐项填。**第 4 项（没证明什么）必须写满 5 条以上。**

### 7.2 提交前

```bash
python 09_repro_scripts/check_g0.py 33_治理模板_G0/<你的报告>.md
```

输出三种：

| 结果 | 含义 | 处理 |
|---|---|---|
| `PASS` | 无红线命中 + 七项齐全 + C 级标注存在 | 可提交 |
| `WARN` | 有可疑表述但可能是引用；或缺少 C 级标注 | 人工复核每一行 |
| `FAIL` | 命中红线且非引用上下文；或缺七项自检 | **不可提交** |

### 7.3 审核方那边

`check_g0.py` 是独立的，只依赖标准库。审核方可以直接对我们的任何一份报告跑一遍——**这就是把"治理"从口头承诺变成可验证的东西**。
