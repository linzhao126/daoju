## §0　结论（四句，D-04 后）

1. **审核说的"按分组单独计件会漏掉跨组的切削暴露、甚至重新选取基线"是真的，而且能复现**：同一把刀做 A 程序 30 件后切到 B 程序 20 件，系统显示 `used = 20`，**前 30 件凭空消失**。真实案例是 c33：**107 件 = prog20 的 51 + prog19 的 56**。
2. 根因不是"选了错的分组"，而是**把物理刀龄（一把刀用了多少件）和统计基准（这类刀通常能用多少件）用了同一个程序过滤条件**。前者**不能加任何程序过滤**，后者按主程序过滤才对。
3. **修法比原方案简单**：`pieces` 整库只有 T1111、无刀号列 → `used = COUNT(*) WHERE allnum > base` 即物理件数。**D1/D2/D3 已在 `60-00 附录D` 用一行 SQL 修完**，不需要新表。
4. **R03 剩余的真问题是"起点"**：`tool_events` 为 0 行 → 系统从未被人工确认过"这把是新刀" → 所有刀龄都是冷启动推断值。`tool_life` 表只在**多把刀共用一库**或**需要分段留痕**时才需要，属未来可选。

## §2　复现证据（内存库，30 行代码，可重跑）

构造：同一物理刃口，先在 prog 11 做 30 件，再切 prog 16 做 20 件，**中途未换刀**；员工在做 prog 11 时点过"已换新刀"。
（真实案例：c33 = prog20 的 51 件 + prog19 的 56 件 = 107 件）

```
prog=11  last_new=0      base=0    used=30   gkey=grant_11_0
prog=16  last_new=None   base=30   used=20   gkey=grant_16_30
物理刃口真实累计 used=50

【缺陷1】last_new 按程序过滤 → 切程序后查不到，base 从 0 重置为 30
【缺陷2】used 从 30 掉到 20，丢失 30 件（真实应为 50）
【缺陷3】gkey 从 grant_11_0 变成 grant_16_30 → 之前锁存的延长许可读不到，会重新评估
```

**这不是理论推演**：SQL 与 `compute_view()` 里逐字一致，只把 `db()` 换成内存库。

## §3　概念模型（审核要求的四个标识）

| 标识 | 含义 | 谁产生 | 用途 |
|---|---|---|---|
| `PhysicalToolLifeId` | 一把刀从装上到拆下 | 新增 `tool_life` 表 | **物理刀龄唯一依据** |
| `ProgramSegmentId` | 一次连续用同一程序加工的一段 | 新增 `segment` 表 | 追溯工况变化、分阶段算 HI |
| `ToolInvocationIndex` | 第几次调用这把刀（同一刃口内的程序切换次数） | `segment` 序号 | 诊断"切了几次程序" |
| `ExposureBySegment` | 每个程序段各自的件数 | `pieces` 按 segment 汇总 | 回答"这 50 件里 30 件在 02、20 件在 03" |

**关键区分**：`ObservedPieceCount`（看到多少件）= 该 `tool_life_id` 下 `pieces` 行数，**不分 prog**。审核要求的正是这个。

## §4　表结构（DDL，只加不删）

```sql
-- ① 物理刃口
CREATE TABLE IF NOT EXISTS tool_life(
  id            INTEGER PRIMARY KEY,
  start_ts      TEXT NOT NULL,
  start_allnum  INTEGER,              -- 起算的全局件号，可空
  end_ts        TEXT,                 -- 空 = 仍在用
  end_reason    TEXT,                 -- 'new'|'replace'|'ledger'|'unknown'
  confirm_src   TEXT NOT NULL,        -- 'operator'|'ledger'|'inferred'
  note          TEXT,
  valid         INTEGER DEFAULT 1
);

-- ② 程序段（同一刃口内，程序发生变化就切一段）
CREATE TABLE IF NOT EXISTS segment(
  id            INTEGER PRIMARY KEY,
  tool_life_id  INTEGER NOT NULL REFERENCES tool_life(id),
  prog          INTEGER NOT NULL,
  prog          INT,                  -- 主程序（D-04：不用品番）
  start_allnum  INTEGER,
  end_allnum    INTEGER,
  start_ts      TEXT,
  end_ts        TEXT
);
CREATE INDEX IF NOT EXISTS ix_seg_tl ON segment(tool_life_id, start_allnum);

-- ③ pieces 挂刃口（可空，双写期允许为空）
ALTER TABLE pieces ADD COLUMN tool_life_id INTEGER REFERENCES tool_life(id);
CREATE INDEX IF NOT EXISTS ix_pieces_tl ON pieces(tool_life_id);
```

**为什么 `pieces` 不存 `segment_id`**：每件都要判断"是否切了程序"，写路径变复杂、且历史回填时容易错。用 `allnum` 区间回溯 segment 即可（`segment.start_allnum <= pieces.allnum <= segment.end_allnum`），查询一次 join 就够。

## §5　迁移路径（5 步，每步可独立回滚）

| 步 | 动作 | 回滚方式 | 验收 |
|---|---|---|---|
| **M1** | 建 `tool_life` / `segment` 表 + `pieces.tool_life_id` 列 | `DROP` 新表、`ALTER TABLE pieces DROP COLUMN`（SQLite 3.35+ 支持） | `PRAGMA integrity_check` OK；现有查询结果逐位不变 |
| **M2** | 回填 `tool_life`：以 `tool_events(event='new')` 为切点；无事件的按 `pieces` 时间断档（>30 分钟）推断，标 `confirm_src='inferred'` | 清空新表 | **回填覆盖率**：能对上 `allnum` 边界的比例 ≥ 90%（低于 90% 停在这里，不进 M3） |
| **M3** | 回填 `pieces.tool_life_id`（按 `allnum` 落区间） | `UPDATE ... SET tool_life_id=NULL` | 覆盖率 100%；`== NULL` 的行数 = 0 |
| **M4** | **双口径并行**：`compute_view()` 同时算 `used_phys` 与 `used_part`，页面并列显示两个数 | 关掉 `USED_MODE` 环境变量即回旧行为 | 影子期内两数差异逐条有解释（每次差异都要能说出是哪个程序段漏计） |
| **M5** | 判定切到 `used_phys`；`used_part` 保留为审计列 | `USED_MODE=part` 切回 | T1~T4 全过（§6） |

**M4 必须存在**，不能直接从 M3 跳到 M5：审核要的是"影子期观察"，不是直接换掉判定依据。

## §6　测试用例（判定标准写死）

| # | 场景 | 构造 | 判定 |
|---|---|---|---|

## §8　风险（如实列，不粉饰）

| 风险 | 现在的实际情况 | 对策 |
|---|---|---|
| **`tool_events` 是 0 行** | 快照里一条"已换新刀"记录都没有 → 说明**系统从未被人工确认过起点**，所有 `tool_life` 都要靠推断 | M2 的 90% 覆盖率门槛就是为这个设的；达不到就停在 M2，**不硬推** |
| **回填错比现状更糟** | 现在虽然漏计，但至少"少算"方向是安全的（提前换刀）；回填错可能造成"多算"→ 延迟换刀 | 回填只允许**保守方向**：拿不准就另起一个 `tool_life`，宁可多切不可少切 |
| **线上 `pieces` 规模未知** | 快照只有 100 行；线上可能有几十万行 | 迁移分批（按 `allnum` 区间），每批校验行数 |
| **`allnum` 是全局计数器** | 9 把刀混流，`allnum` 不是本刀件号 | 只用它做**排序与区间划分**，绝不用差值算件数（这条已在 `server.py:609` 注释里） |
| **SQLite `DROP COLUMN` 版本限制** | 需 3.35+ | M1 回滚前先查 `select sqlite_version()` |
