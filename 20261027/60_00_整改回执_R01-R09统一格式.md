### §0　结论（四句，D-04 后）

1. **审核说的"按分组单独计件会漏掉跨组的切削暴露、甚至重新选取基线"是真的，而且能复现**：同一把刀做 A 程序 30 件后切到 B 程序 20 件，系统显示 `used = 20`，**前 30 件凭空消失**。真实案例是 c33：**107 件 = prog20 的 51 + prog19 的 56**。
2. 根因不是"选了错的分组"，而是**把物理刀龄（一把刀用了多少件）和统计基准（这类刀通常能用多少件）用了同一个程序过滤条件**。前者**不能加任何程序过滤**，后者按主程序过滤才对。
3. **修法比原方案简单**：`pieces` 整库只有 T1111、无刀号列 → `used = COUNT(*) WHERE allnum > base` 即物理件数。**D1/D2/D3 已在 `60-00 附录D` 用一行 SQL 修完**，不需要新表。
4. **R03 剩余的真问题是"起点"**：`tool_events` 为 0 行 → 系统从未被人工确认过"这把是新刀" → 所有刀龄都是冷启动推断值。`tool_life` 表只在**多把刀共用一库**或**需要分段留痕**时才需要，属未来可选。

### §2　复现证据（内存库，30 行代码，可重跑）

构造：同一物理刃口，先在 prog 11 做 30 件，再切 prog 16 做 20 件，**中途未换刀**；员工在做 prog 11 时点过"已换新刀"。
（真实案例：c33 = prog20 的 51 件 + prog19 的 56 件 = 107 件）

```
prog=11  last_new=0      base=0    used=30   gkey=grant_11_0
prog=16  last_new=None   base=30   used=20   gkey=grant_16_30
物理刃口真实累计 used=50

【缺陷1】last_new 按程序过滤 → 切程序后查不到，base 从 0 重置为 30
【缺陷2】used 从 30 掉到 20，丢失 30 件（真实应为 50）
【缺陷3】gkey 从 grant_11_0 变成 grant_16_30 → 之前锁存的延长许可读不到，会重新评估
```

**这不是理论推演**：SQL 与 `compute_view()` 里逐字一致，只把 `db()` 换成内存库。

### §3　概念模型（审核要求的四个标识）

| 标识 | 含义 | 谁产生 | 用途 |
|---|---|---|---|
| `PhysicalToolLifeId` | 一把刀从装上到拆下 | 新增 `tool_life` 表 | **物理刀龄唯一依据** |
| `ProgramSegmentId` | 一次连续用同一程序加工的一段 | 新增 `segment` 表 | 追溯工况变化、分阶段算 HI |
| `ToolInvocationIndex` | 第几次调用这把刀（同一刃口内的程序切换次数） | `segment` 序号 | 诊断"切了几次程序" |
| `ExposureBySegment` | 每个程序段各自的件数 | `pieces` 按 segment 汇总 | 回答"这 50 件里 30 件在 02、20 件在 03" |

**关键区分**：`ObservedPieceCount`（看到多少件）= 该 `tool_life_id` 下 `pieces` 行数，**不分 prog**。审核要求的正是这个。

### §4　表结构（DDL，只加不删）

```sql
-- ① 物理刃口
CREATE TABLE IF NOT EXISTS tool_life(
  id            INTEGER PRIMARY KEY,
  start_ts      TEXT NOT NULL,
  start_allnum  INTEGER,              -- 起算的全局件号，可空
  end_ts        TEXT,                 -- 空 = 仍在用
  end_reason    TEXT,                 -- 'new'|'replace'|'ledger'|'unknown'
  confirm_src   TEXT NOT NULL,        -- 'operator'|'ledger'|'inferred'
  note          TEXT,
  valid         INTEGER DEFAULT 1
);

-- ② 程序段（同一刃口内，程序发生变化就切一段）
CREATE TABLE IF NOT EXISTS segment(
  id            INTEGER PRIMARY KEY,
  tool_life_id  INTEGER NOT NULL REFERENCES tool_life(id),
  prog          INTEGER NOT NULL,
  prog          INT,                  -- 主程序（D-04：不用品番）
  start_allnum  INTEGER,
  end_allnum    INTEGER,
  start_ts      TEXT,
  end_ts        TEXT
);
CREATE INDEX IF NOT EXISTS ix_seg_tl ON segment(tool_life_id, start_allnum);

-- ③ pieces 挂刃口（可空，双写期允许为空）
ALTER TABLE pieces ADD COLUMN tool_life_id INTEGER REFERENCES tool_life(id);
CREATE INDEX IF NOT EXISTS ix_pieces_tl ON pieces(tool_life_id);
```

**为什么 `pieces` 不存 `segment_id`**：每件都要判断"是否切了程序"，写路径变复杂、且历史回填时容易错。用 `allnum` 区间回溯 segment 即可（`segment.start_allnum <= pieces.allnum <= segment.end_allnum`），查询一次 join 就够。

### §5　迁移路径（5 步，每步可独立回滚）

| 步 | 动作 | 回滚方式 | 验收 |
|---|---|---|---|
| **M1** | 建 `tool_life` / `segment` 表 + `pieces.tool_life_id` 列 | `DROP` 新表、`ALTER TABLE pieces DROP COLUMN`（SQLite 3.35+ 支持） | `PRAGMA integrity_check` OK；现有查询结果逐位不变 |
| **M2** | 回填 `tool_life`：以 `tool_events(event='new')` 为切点；无事件的按 `pieces` 时间断档（>30 分钟）推断，标 `confirm_src='inferred'` | 清空新表 | **回填覆盖率**：能对上 `allnum` 边界的比例 ≥ 90%（低于 90% 停在这里，不进 M3） |
| **M3** | 回填 `pieces.tool_life_id`（按 `allnum` 落区间） | `UPDATE ... SET tool_life_id=NULL` | 覆盖率 100%；`== NULL` 的行数 = 0 |
| **M4** | **双口径并行**：`compute_view()` 同时算 `used_phys` 与 `used_part`，页面并列显示两个数 | 关掉 `USED_MODE` 环境变量即回旧行为 | 影子期内两数差异逐条有解释（每次差异都要能说出是哪个程序段漏计） |
| **M5** | 判定切到 `used_phys`；`used_part` 保留为审计列 | `USED_MODE=part` 切回 | T1~T4 全过（§6） |

**M4 必须存在**，不能直接从 M3 跳到 M5：审核要的是"影子期观察"，不是直接换掉判定依据。

### §8　风险（如实列，不粉饰）

| 风险 | 现在的实际情况 | 对策 |
|---|---|---|
| **`tool_events` 是 0 行** | 快照里一条"已换新刀"记录都没有 → 说明**系统从未被人工确认过起点**，所有 `tool_life` 都要靠推断 | M2 的 90% 覆盖率门槛就是为这个设的；达不到就停在 M2，**不硬推** |
| **回填错比现状更糟** | 现在虽然漏计，但至少"少算"方向是安全的（提前换刀）；回填错可能造成"多算"→ 延迟换刀 | 回填只允许**保守方向**：拿不准就另起一个 `tool_life`，宁可多切不可少切 |
| **线上 `pieces` 规模未知** | 快照只有 100 行；线上可能有几十万行 | 迁移分批（按 `allnum` 区间），每批校验行数 |
| **`allnum` 是全局计数器** | 9 把刀混流，`allnum` 不是本刀件号 | 只用它做**排序与区间划分**，绝不用差值算件数（这条已在 `server.py:609` 注释里） |
| **SQLite `DROP COLUMN` 版本限制** | 需 3.35+ | M1 回滚前先查 `select sqlite_version()` |

### §1　裁决原文与我的执行口径

**原文**：「按主程序，分这把刀干了多少件，不要使用品番」

拆成两条互不冲突的口径：

| 口径 | 问题 | 怎么算 | 依据 |
|---|---|---|---|
| **A 物理件数** | 这把刀**一共**干了多少件 | `COUNT(*) FROM pieces WHERE allnum > base`（**不加程序过滤**） | 「这把刀」是物理刃口，不是某个程序 |
| **B 统计基准** | 这**类**刀通常能干多少件 | `history WHERE prog = 当前主程序` | 您说的「按主程序」作用在统计分组上 |

**两者必须分开**，因为混用会同时犯两种错：按 A 去算基准 → 把不同程序的寿命混成一堆；按 B 去算件数 → 跨程序的件凭空消失（c33）。

> ⚠ **本表还差一步**（2026-10-29 晚补）：口径 A 现在数的是**物理件数**，但不同程序"一刀能用多少件"不同（M0 105.5 vs 82.5，差 1.28 倍），
> 所以严格做法是**当量折算** `Σ(pᵢ/M0ᵢ)` —— 生命周期仍是一条，只是件数按各程序基准加权。
> 实测 c34：物理 117 件 = 41@prog19 + 76@prog14，只数当前程序会低估消耗 **38 个百分点**。详见 `60-00 附录F`。

| 位置 | 改前 | 改后 | 为什么 |

### §0　结论（五句）

1. **28 个周期里只有 23 个可判**，另 5 个（c33/c55/c56/c57/c58）同主程序历史 <3 把 → 线上显示「—」（D-04 的代价，见 `60-00 附录D` §3.1）。
2. **放行的 12 把里，10 把真的活过 90% 线（83%）**；**拦截的 11 把里，有 6 把本来能活过（55% 误拦）**。按件数算：**提前换掉 820 件、超期用 6 件**；而"完全不用信号、一律数到 90%"是 **提前换 428 件、超期 101 件**。**信号分支用多浪费 392 件产能，换掉 95 件超期风险。**
3. **锁存点几乎是任意的**：23 个可判周期里 **13 个（57%）**如果换一件复判，结论会翻转；最多的一把翻了 **9 次**。
4. **机制找到了**：复核点后 10 件内 `hi_now` 的极差中位 **0.93%（最大 4.51%）**，而判据是 **1%**。**43% 的周期，噪声幅度本身就超过判据门限**——所以"在哪一件上评估"直接决定结论。
5. **反事实**：把复核点从 40% 挪到 90%，16 个可比较周期里 **5 个（31%）结论改变**。**这个分支的可靠性目前取决于评估时点，而不取决于刀的状态。**

### §2　放行是否正确（这是审核最关心的一条）

### §3　锁存 vs 逐件复判

线上逻辑：跨过 `b` 时评估一次，`kv_set` 锁存，之后不再变。

把 `[b, min(h, life)]` 区间逐件复判（同一套 `hi_now` / `TAU`）：

| 指标 | 值 |
|---|---|
| 发生过翻转的周期 | **13 / 23（57%）** |
| 翻转次数中位 | 1 |
| 翻转次数最大 | **9**（c36、c52） |
| 首次翻转最早发生在 | `b+1`（c36，b=32 → 33 件就翻） |

**c36 最典型**：`b=32`、`h=72`、`b 处 HI=1.0062` → 判"拦截"，上限 32；但它活了 **99 件**。逐件复判在 34 件就翻了，之后又翻 8 次——**这条曲线在门限上反复横跳，说明 1% 这个门限就在噪声里**。

### §4　机制：噪声幅度 > 判据门限

`b` 之后 10 件内 `hi_now` 的波动：

| 指标 | 值 |
|---|---|
| 极差 中位 | **0.93%** |
| 极差 最大 | **4.51%** |
| 标准差 中位 | 0.29% |
| 极差 > 1%（判据）的周期 | **10 / 23（43%）** |

判据 `TAU=1%`，而复核点附近的极差中位就是 0.93%。**等于拿一根和噪声一样粗的尺子量东西，量出来的结果取决于你站哪一件。**

这条与 MEMORY 里记的机制一致：`W=10` 的中位滤波只能把单件噪声压到 σ/√10 ≈ 0.6%，但**同一批里还有工序/余量波动**，压不掉。

### §5　反事实：复核点挪到 h

| 指标 | 值 |
|---|---|
| 可比较周期（活到 h） | 16 |
| 结论改变 | **5（31%）** |
| 改变方向 | 3 个 ✓→✗（c29/c35/c52）、2 个 ✗→✓（c36/c39） |

**换一个评估点，31% 的刀结论就变。** 所以"40% 处锁存"这个设计**没有工程依据**——它是 2026-10-20 调参时选中的一个点（嵌套 CV 16 次中 15 次选中该参数组合），但那是在**成本口径**下选的，不是在"结论稳定性"下选的。

### §1　先把「为什么会少算」说清：不是设计意图，是 SQL 写错

旧代码（`server.py` 原 614 行）：

```sql
used = SELECT COUNT(*) FROM pieces WHERE prog IN (当前分组) AND allnum > base
```

`prog IN (...)` 这个条件把**不属于当前程序段的件排除在计数之外**。c33 的 107 件在库里是连续的生命周期，但因为前 51 件的程序号是 20、后 56 件是 19，SQL 只数了 56。

**这不是"按程序拆生命周期"的设计，恰恰是"计件时误用了统计分组"的 bug。** 我上一轮的表述容易读成"我在主张按程序拆"，是我说得不对。

已修：`used = SELECT COUNT(*) FROM pieces WHERE allnum > base`（去掉程序过滤）。**生命周期是一条**，这一点没有争议。

---

### §2　但您后半句点出了第二个问题：不同程序，刀能用多少件不同

实测（28 周期，剔 c38/c51）：

| 主程序 | 刀数 | 寿命逐把 | 中位 M0 | CV |
|---|---|---|---|---|
| 20 | 6 | 92, 95, 107, 109, 104, 108 | **105.5** | 7.1% |
| 11 | 7 | 97, 109, 47, 83, 89, 80, 68 | **83.0** | 24.6% |
| 14 | 8 | 52, 80, 76, 85, 99, 50, 90, 92 | **82.5** | 23.2% |
| 17 | 2 | 81, 102 | 91.5 | — |
| 13 | 1 | 96 | 96.0 | — |
| 16 | 1 | 43 | 43.0 | — |
| 19 | 1 | 107 | 107.0 | — |

**最大/最小 = 105.5 / 43 = 2.49 倍**；即便只看有 6~8 把刀的三个程序，也有 **105.5 vs 82.5 = 1.28 倍**。

所以「总件数 vs 单一 M0」同样不准：**同样干 40 件，在 prog20 上只消耗 38% 寿命，在 prog14 上消耗 48%。**

### §3　正确口径：当量消耗（生命周期不拆，件数按程序折算）

$$\text{消耗率} = \sum_i \frac{p_i}{M0_i}$$

- $p_i$ = 这个生命周期里在程序 $i$ 上干的件数
- $M0_i$ = 程序 $i$ 的历史寿命中位
- **判定线不变**：复核点 0.4、延长线 0.9，只是从"件数"换成"消耗率"

这不是拆生命周期：**分母按程序分，分子仍然全生命周期累计**。

#### 3.1 四个多程序周期的实测（`life_program_segments.csv`，逐件切分）

全库 20 个有逐件分段的周期里，**4 个是多程序（20%）**：

| 周期 | 段明细 | 物理件数 | 只数当前程序 | **当量消耗** | 差多少 |
|---|---|---|---|---|---|
| c27 | 6@14 + 92@20 | 98 | 92 | 0.945 | −0.04 |
| c33 | 51@20 + 56@19 | 107 | 56 | **1.007** | **−0.48** |
| c34 | 41@19 + 76@14 | **117** | 76 | **1.304** | **−0.38** |
| c38 | 195@14 + 2@11 | 197 | — | 2.388 | 已排除 |

**c34 是最能说明问题的**：
- 只数当前程序（prog14 的 76 件）→ 76 / 82.5 = **0.92**，系统认为"还剩 8% 余量"
- 真实当量 → 41/107 + 76/82.5 = **1.304**，**已经用掉 130%**

**差 38 个百分点。这不是精度问题，是会直接把刀用崩的量级。** 您说的"不同程序次数不同"，落在这个数上就是 38%。

### §5　做当量折算的可行性限制（必须先说）

1. **4 个程序样本 <3 把**（13/16/17/19），M0 不可靠。c33 用到的 prog19 就是"单把 107"。
2. 若某段程序的 M0 不可靠，折算结果同样不可靠 → **不能假装算得很准**。
3. 需要逐件的程序归属：线上 `pieces` 表**有 `prog` 列**（每件一条），所以当量折算在线上**是可以算的**，不需要新表。

#### 我的建议（需您批准）

| **B 条件折算**（我倾向） | 段程序的 M0 有 ≥3 把才折算；否则该段按"物理件数 / 当前程序 M0"处理，并在页面标注该段基准为"弱" | 混合口径，需在页面说清 |
| **C 暂不折算** | 只保留物理件数（现状） | c34 这类会低估 38% |
