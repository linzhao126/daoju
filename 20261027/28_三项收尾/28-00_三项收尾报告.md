## §2　任务 2：修 M1-新 的数值爆炸

### 2.1 病灶

```python
pred = m0b · exp(g · z)      # g 已 clamp ±0.5，但 z 没有上限
```

训练池只有 2~3 把刀时 `sd` 极小 → `z` 放大 → `exp` 爆炸。

实测最坏：**c60 @N=40 预测 344.69 件**（真值 52，该刀总寿命仅 92）。
另一例：c27 @N=40 预测 220.1 件（真值 52，M0-B 给的是 67）。

### 2.2 改法（`bt_core.py`）

```python
Z_PRED_MAX = 3.0                    # 测试点的 z 截断
FACTOR_LO, FACTOR_HI = 0.5, 2.0     # 乘性因子区间
PRED_CAP_MULT = 3.0                 # 绝对值兜底

z_k    = clip((r_k − mean) / sd, −Z_PRED_MAX, Z_PRED_MAX)
factor = clip(exp(g · z_k), FACTOR_LO, FACTOR_HI)     # ← 关键
pred   = clip(m0b × factor, 0, PRED_CAP_MULT × m0b)
```

**为什么因子限制在 [0.5, 2.0]**：一个"修正项"不该改变预测的量级。M0-B 的误差本身已有 10~15 件，再乘 3 倍就变成 30~45 件。

**为什么只截断测试点的 z**：拟合时的 `z` 不动 → `FitG` 语义不变 → **Test-A 仍通过**（已验证）。

### 2.3 效果：MAE 全面改善，没有一处变差

`grouping_test.csv` 的 `AbsM1New`，修前 vs 限幅后：

| 组 | N=20 | N=40 | N=60 | N=80 |
|---|---|---|---|---|
| global_all | 22.96 → 22.42 (−0.55) | 24.05 → **21.50** (−2.55) | 16.85 → 16.85 | 17.16 → 17.16 |
| global_drop | 18.91 → 18.02 (−0.89) | 20.90 → **18.50** (−2.39) | 11.52 → 11.52 | 9.02 → 9.01 |
| part_all | 25.89 → 25.74 (−0.15) | 26.58 → **22.72** (−3.86) | 17.36 → 17.32 | 16.71 → 16.62 |
| **part_drop** | 19.98 → 19.70 (−0.28) | 21.49 → **17.33 (−4.16)** | 11.24 → 11.21 | 8.52 → 8.37 |
| prog_all | 28.73 → 28.14 (−0.60) | 25.19 → 23.28 (−1.91) | 21.29 → 21.02 | 19.33 → 19.30 |
| prog_drop | 16.40 → 16.21 (−0.19) | 17.53 → **15.97** (−1.56) | 13.51 → 13.34 | 10.66 → **9.57** (−1.09) |

**24 个格子里 21 个改善、3 个持平、0 个变差。** 改善集中在 N=40（−1.56 ~ −4.16），正是爆炸最严重的位置。

| 项 | 修前 | 限幅后 |
|---|---|---|
| `max\|M1New\|` | 220.1 | **134.5** |
| 因子触上限的比例 | — | 2% |
| 因子触下限的比例 | — | 3% |

**触界只占 5%，说明限幅没有普遍破坏正常预测，只掐掉了极端的。**

### 2.4 但仍然没有解决根问题

限幅后最大预测 134.5 件，真值 60 件 —— 误差仍 74 件。

原因：**M0-B 本身给了 69（真值 60），乘 2 倍就是 138。** 限幅只能挡住"乘 3 倍以上"，挡不住"乘 2 倍"。

**所以真正的结论是**：

> M1-新 的乘性结构会**放大 M0-B 已有的误差**。这不是数值问题，是模型结构问题。
> 护栏解决了"输出无界"（不再给出 344 件这种物理上不可能的值），但解决不了"放大"。

要解决放大，只能改结构（比如改加性修正、或让 `g` 随样本量收缩），那属于重新设计模型，不在本轮范围。

## §6　过程中踩到并修掉的一个坑：行尾符被整体改写

### 现象

改完 `server.py` 后 `diff` 显示 **2052 行变更**，但我只改了几十行。

### 原因

`server.py` 原版是 **LF**，我用 Python 文本模式 `open(p,'w')` 回写，Windows 下会把 `\n` 转成 `\r\n`（CRLF），于是**整个文件都变了**。

真实差异只有 **98 行**（`diff --strip-trailing-cr` 验证）。

### 为什么这个坑要紧

1. **Git 里整个文件显示为已修改**，审核方看不出到底改了什么，会怀疑"是不是偷偷换了内容"；
2. 这个项目里 CRLF 是主流（171 个文件 CRLF / 84 个 LF，因为 pandas `to_csv` 在 Windows 默认写 CRLF），所以**不能一刀切全改成 LF**；
3. 判断标准只能是：**改之前是什么格式，改之后必须保持一致**。

### 修法

| 文件 | 原格式 | 处理 |
|---|---|---|
| `server.py` | LF | 转回 LF（改动 2052 → **98** 行） |
| `index.html` | LF | 转回 LF（改动 1011 → **7** 行） |
| `bt_core.py` | LF | 转回 LF（改动 169 → **21** 行） |
| `s30`~`s39`（今天新建/改的） | 混杂 | 统一为 **LF**（与 Write 工具默认一致） |
| `s0x`/`s2x`（历史脚本） | CRLF | **不动**（避免制造无意义 diff） |

### 教训

> **用脚本改文件时，必须用二进制模式回写，或显式指定 `newline=''`。**
> 否则一行改动会变成整个文件的改动，在 code review 里等于把真正的修改藏起来了。

后续凡是用 Python 批量改写已有文件，都要先记下原行尾符，改完校验 `diff` 行数是否与预期相符。
