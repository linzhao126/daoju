# 换刀决策系统（FastAPI + 页面 + SQLite）

不是单文件演示页。现在是一条真链路：**采集流（模拟或 influx）→ SQLite → 件内对齐 → HI → 两级判定 → 页面**。后端是 **FastAPI**。

两种数据源，用 `--source` 切：

| 模式 | 命令 | 用途 | 数据库 |
|---|---|---|---|
| `sim`（默认） | `python server.py` | 模拟器造数据，演示判定逻辑和按钮流程 | `data/tool_sim.db` |
| `influx` | `python server.py --source influx` | 直连车间 influx（`<influxdb主机>:8086`），拉真实 T1111 数据 | `data/tool.db` |

> ⚠ **两个模式默认用不同的库文件**（2026-10-21 修）。原来都用 `data/tool.db`，实测踩到：先用 influx 回填真实数据，再开模拟器演示，29 件假数据（allnum 57800 段）直接灌进真实库，`pieces` 从 37 变 66，而且因为还在 7 天保留期内，清理策略不会删它们，只能手工挑出来删。
>
> 要指定别的库：`--db /path/to/x.db`。

> 📖 **五张表、每个字段是干什么的、实测取值、常用排查 SQL → [`数据库字段说明.md`](数据库字段说明.md)**

## 怎么跑

```bash
cd 2ndPrediction/tool_log
../../.venv/Scripts/python.exe server.py                    # 模拟器（写 tool_sim.db）
../../.venv/Scripts/python.exe server.py --source influx    # 真实采集（写 tool.db）
# 页面     http://127.0.0.1:8765/
# 接口文档 http://127.0.0.1:8765/docs
```

机床旁平板要访问（同一局域网）：

```bash
../../.venv/Scripts/python.exe server.py --host 0.0.0.0
```

开发时改代码自动重载：

```bash
../../.venv/Scripts/python.exe server.py --reload
```

依赖：`fastapi` + `uvicorn` + `numpy`（已装在 `.venv`）。`influx_source.py` **只用标准库**（urllib），不需要 `requests`。

> 厂里机器装不了包时，用 `server_stdlib.py` —— 标准库 `http.server` 版，接口和页面完全一样，只少了 `/docs` 和参数校验。**但它没有 influx 接入和保留策略**，只适合演示。

## 五个文件

| 文件 | 作用 |
|---|---|
| `simulator.py` | 生成模拟采集数据（一件 60 行，含 8 行换刀位）。另含 `align_piece()` 件内对齐、`z_band_keep()` Z 带、`median_from_curve()` 曲线重算 |
| `influx_source.py` | **真实数据源**：`InfluxPuller` 按水位线窗口拉 influx，服务端 pivot 后过滤刀号 |
| `server.py` | **主入口（FastAPI）**：路由 + SQLite + 封口 + 两级判定 + 保留策略 |
| `server_stdlib.py` | 零依赖备选版（标准库 http.server），接口一致，装不了包时用 |
| `index.html` | 页面。每 700ms 轮询后端 |

## 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/` | 页面 |
| GET | `/api/state` | 页面轮询的完整状态（件数、M0、HI、许可、状态） |
| POST | `/api/event` | `{event: new/hold/fail, reason}` 员工点击 |
| POST | `/api/undo` | 撤销上一次点击 |
| POST | `/api/sim` | `{action: start/stop/speed/prog/reset}` 模拟器控制（influx 模式下页面上整块隐藏） |
| GET | `/api/health` | 存活探针 + 拉取统计 + 清理统计 |
| POST | `/api/maintenance` | 手动跑一次保留策略清理（运维/测试用） |
| GET | `/docs` | FastAPI 自带的可交互接口文档 |

请求体用 Pydantic 校验：漏字段 / 类型错会返回 **422 + 结构化错误**，不会像原版那样抛 500。

## 并发模型（改成 FastAPI 后最关键的一处）

- 路由全部用**同步 `def`** → FastAPI 自动丢进线程池，不做成 `async`。因为 numpy 和 sqlite3 都是阻塞的，写成 async 反而会卡住事件循环。
- SQLite 连接用 `threading.local()`，**一个请求线程一个连接**（连接不能跨线程共享）。
- 写操作统一走 `_wlock`（`RLock`）串行化 —— WAL 模式只允许一个写者，不加锁会 `SQLITE_BUSY`。
- `busy_timeout=5000` 兜住跨线程的短暂争用。
- 退出时执行 `PRAGMA wal_checkpoint(TRUNCATE)`，把 `-wal` 合并回主库。

> 顺带一提：`data/` 下除了 `tool.db`，还会看到 `tool.db-wal` 和 `tool.db-shm`。这是 WAL 模式的正常产物（预写日志 + 共享索引），**不要单独删**，进程正常退出时会自动合并并清除。

## 数据流

```
[sim]    Simulator 线程        一件 60 行
[influx] InfluxPuller 线程     15 秒一批（水位线窗口）
              │
              ▼
raw_rows 表  ←── 原始层：一行一个采样瞬间，未聚合/未对齐/未归一化
              │      ts 定长 UTC + UNIQUE，重复拉取靠 INSERT OR IGNORE 挡掉
              │  按 allnum 封口（同一 allnum 的行 = 一件）
              │  延迟 120 秒才封：一件的最后几行常和后一批一起到
              ▼
件内处理：① 先裁 x∈[18,41] ② Z 带过滤（只留 |z−z0|≤1mm 的行）
          ③ 按 x_pos 插值到 19~40 / 40 点网格
          ④ 丢掉 <50% 中位的点 ⑤ 取中位
              ▼
pieces 表（一件一行：load_med + 40 点 curve）
              │  HI = load_med ÷ 前 20 件 load_med 的中位
              ▼
HI 序列
              │
两级判定：0.4×M0 触发 → 看 HI 是否已 ≥1% → 给延长许可 → 0.9×M0 硬上限
              ▼
GET /api/state ──> 页面轮询
```

**为什么必须先对齐 X 再算**：一件工件内部，光是"刀走到哪儿"就让负载变 80%；而刀从新到废只抬 3%。不对齐，比的是几何不是磨损。这一步就是 `t1111_pipeline.py xalign` 的核心。

**为什么还要先裁 x 段**（2026-10-21 实测补上）：真实 T1111 一件 143 行里只有约 79 行的 x 落在 19~41，其余是 x≈238 的快进/换刀位和 x≈0 的中心收尾。不裁的话这些点会进入插值序列，把 19 和 40 两个端点带偏。另加一条"覆盖不足直接判无效"：x 最小值 >22 或最大值 <37 时不做插值（全靠外推等于编数）。

**Z 带怎么定位切断工步**（2026-10-21 补，`simulator.z_band_keep`）：把 x 段内剩余行的 z 排序，相邻差 >2mm 就切层，选 **x 扫掠跨度最大**的那层（切断的物理特征就是"Z 锁定 + X 从 40 扫到 19"，跨度必然是最大的一层），最后按 |z−该层中位| ≤1mm 保留。

> ⚠ 第一版写的是"取 z 的众数"，**实测被推翻**：只要 z 带一点抖动（伺服跟随误差 ±0.05mm 很常见），`round(z,1)` 会把同一工步打散成 −38.3/−38.4/−38.2，而干扰工步的值恰好精确 → 干扰反而赢。实测：给一件掺 52 行 z=189.36 后，众数选中 189.36，把真正切削的 52 行全剔了，load_med 从 42.2 涨到 92.9。

**Z 带到底值多少（实测，别高估）**：

| 场景 | 无 Z 带 | 有 Z 带 |
|---|---|---|
| 干扰 10 行（少于切削行） | load_med 不变 | 不变 |
| 干扰 52 行（与切削行同数） | 不变 | 不变 |
| **干扰 120 行（多于切削行）** | **42.2 → 90.0（+113%）** | **不变** |

因为 `load_med` 取中位数，天然抗少量污染点。**所以 Z 带的真实价值不是"提高精度"，而是**：① 干扰占多数时是唯一防线；② 与离线 xalign 口径一致（否则阈值 0.4/0.9 不可照搬）；③ 存下来的 `curve` 以后要做斜率/均值分析时，污染点会直接进结果，中位数挡不住。

2026-10-21 真实数据现状：切断段内 z 只有一个值（−32.3），即 Z 带当前走"单层 → 不过滤"分支，是空转的第二道防线。

**仍比离线简化的是"X 单调下降段 + 啄切容差 2.5mm"**：线上是增量封口，要在"这件收齐"时立刻出结果，而单调段提取依赖完整时间序列回溯；且啄切容差(2.5mm)与真实退刀(退到 x=40，+40mm)只差 16 倍，参数错了会静默切错段。当前"x 段 + Z 带 + 负载门控"已能把非切削行剔干净，先不引入这个参数风险。

**`pieces.curve` 存什么、为什么**：存"插值后、门控前"的 40 个原始对齐值（紧凑 JSON，实测 313~384 字符），**不存 HI、不存归一化值**——归一化需要基线，而基线会随算法变。存原始值才能任何时点重算。

```python
curve = json.loads(row["curve"])
load_med = simulator.median_from_curve(curve)   # 与 align_piece 同口径，实测差 3e-05（round 到 4 位造成）
```

这样 raw_rows 满 7 天被删之后，30 天内仍可换门控规则、换基线、换算法重算，不必重采。

## 保留策略（滚动删除）

| 表 | 保留 | 最小保留量 | 说明 |
|---|---|---|---|
| `raw_rows` | 7 天 | 最近 50,000 行 | 原始层，可回溯窗口 |
| `pieces` | 30 天 | 最近 300 件 | 派生层，一件一行，体积很小 |
| `history` | **永久** | — | M0 / P85 的唯一依据，只有十几条 |
| `tool_events` | **永久** | — | 换刀台账，重建刀身份的唯一凭据 |

**关键：cutoff 用数据水位线，不用系统时钟。**

```
W = MAX(ts)          -- 数据自己走到哪儿
cutoff = W - 7天
```

为什么不能用 `now - 7天`：放假 10 天，程序一启动时 `max(ts)` 已经是 10 天前，所有数据都早于 `now-7d`，一次 DELETE 就把库删空。改用 W 之后，放假 7 天 / 10 天 / 30 天，W 都不动，cutoff 也不动，**一行都不删**。

实测（临时库，每 6 小时一行，共 20 天）：

| 场景 | 结果 |
|---|---|
| 正常生产 | raw 80→29，留下 7.0 天 |
| 放假 7 天 | raw 80→29，留下 7.0 天（**没删空**） |
| 放假 10 天 | raw 80→29，留下 7.0 天 |
| 放假 30 天 | raw 80→29，留下 7.0 天 |

第二层保险是双条件：**既早于 cutoff，又不在最近 MIN_* 条之内**，两个都满足才删。行数少于 `MIN_RAW_ROWS` 时 `OFFSET` 返回 NULL，一行都不删。

清理节拍：启动时一次 + 每小时一次（不跟着 15 秒拉取跑，DELETE 写 WAL 太频繁）。

> 设备永久停机时，水管线冻住，库不会缩。这是**有意为之**——用户要的是"库里始终有 7 天数据"，不是"文件必须小于多少 MB"。真要控体积，用"水位线停滞超过 N 天"告警，别去删数据。

## 数据库

`data/tool.db`（真实）/ `data/tool_sim.db`（演示），五张表：

| 表 | 内容 |
|---|---|
| `raw_rows` | 原始行（`ts` 定长 UTC + UNIQUE, allnum, prog, x_pos, **z_pos**, spindle_load, spindle_speed, feedrate） |
| `pieces` | 件级汇总（allnum, prog, load_med, n_points, ts, **curve** 40 点 JSON） |
| `tool_events` | 员工点击记录（new / hold / fail + 当时件数、状态、原因） |
| `history` | 每把刀完成的真实寿命，`valid=0` 表示疑似漏点不计入 |
| `kv` | 延长许可的锁存状态 + `sealed_upto` 封口游标 |

⚠ **`raw_rows` 只有 7 列，不是 influx 全字段**。准确说法是"原始粒度子集"：保留了"一行 = 一个采样瞬间"的粒度，但字段是从对齐+HI 最小必要集反推的，砍掉了 `L_abso_z` / `L_rate1` / `L_state` / `L_alm_no` / `L_circle_time` / `L_tool_number` / `L_feed_override` / `L_X/Z_servo_load` 等。代价是 Z 带过滤、工步门控、停机报警诊断都做不了，而且 7 天后 raw_rows 一删就彻底回不去。存储其实很便宜（单台约 5 万行/天，全 40 列也就 16MB/天），要补随时可补。

`ts` 必须是**定长**（`YYYY-MM-DDTHH:MM:SS.mmmμμμZ`，27 字符，UTC）：保留策略靠字符串比较 `ts < cutoff`，长度不一（有无毫秒/有无 Z）会让字典序算错。

## 三个按钮

| 按钮 | 什么时候点 | 系统得到什么 |
|---|---|---|
| **已换新刀** | 主动换了 | 计数基准重置 + 这把刀的真实寿命入库 → M0 自己累积 |
| **继续加工** | 系统提示了但你觉得还能干 | 否决样本 + 当时件数，这是唯一能把老师傅经验注入系统的地方 |
| **刀废了** | 崩刀 / 超差 / 表面差 | 失效样本 + 原因；`new` 和 `fail` 都会追加进 `history` |

## 四个数字怎么读

```
同程序最短 50  |  同程序中位 85  |  同程序常见上限 109  |  历史最长 197
```

- **最短 50** = 风险下界，程序 14 有刀只用到 50 件就废了
- **中位 85** = 典型值，**换刀判定只看这一个数**
- **常见上限 109** = P85，15% 的刀活不到这里
- **最长 197** = 7 把里只有 1 把到过，是离群值

P85 只用于显示不用于判定，原因见 `../out/分位数口径对比.txt`：判定基准换成 P85 后失效从 0/16 变 2/16、成本涨 84%（ρ=10）；而且程序 14 只有 7 个样本，P85 的 bootstrap 95% 区间是 [85, 197]，跨度等于点估计本身。

### 样本不够时显示「—」，绝不拿兜底值冒充

这四格本来就是**同一个寿命分布的四种统计**。样本只有 1 条时，`中位 = P85 = 最短 = 最长`，四个数字完全相等 —— 看上去很确凿，其实什么都没说。

真实踩过的坑（2026-10-21）：程序 17 没有历史，代码兜底 `hist=[100.0]`，于是四格全显示 **100**，用户以为系统算出了四个值，实际全是同一个猜的数。

现在的门槛（`server.py` 顶部常量）：

| 统计量 | 最少样本 | 不足时 |
|---|---|---|
| 最短 / 中位 / 最长 | `MIN_N_BASIC = 3` | 显示「—」+「需 ≥3 条历史」 |
| 常见上限 P85 | `MIN_N_P85 = 5` | 显示「—」+「需 ≥5 条历史」 |
| 0.4 / 0.9 判定线 | 需 P85（即 ≥5 条） | 状态降级成 `cnt`，**不给任何"该不该换"的判断** |

样本不足时接口返回 `m0/p85/hmin/hmax/b/h` 全是 `null`，`judge_ok=false`、`state="cnt"`，页面据此：四格画「—」、整条刻度轴不画、状态栏写「件数提示 · 暂不做换刀判定」、说明行写「暂以经验值 100 件作提示线（**不是判定依据**）」。

### 冷启动的件数只能当"≥"

`base_allnum` 取"最后一次点「已换新刀」的件号"，**没人点过就退回 `min(allnum)-1`**。所以冷启动时显示的 `used` 是"库里该程序的件数"，不是这把刀的真实件数——中间换过刀系统是不知道的。

接口用 `base_src` 区分：`event`（点过，精确）/ `cold`（没点过，页面显示 **≥N**）。误差只会偏大 → 提示提前 → 方向安全。

### 四格不随换刀变化

四格统计的是"同程序历史"，跟当前这把刀无关，**换刀后不该变**。换刀只重置三样：`used → 0`、`HI → 基线建立中`、`granted → null`。

## 四级状态与信号

| 件数位置 | 状态 | 页面表现 |
|---|---|---|
| 历史样本不足（<5 条） | `cnt` | 只显示件数 + 四格「—」，**不给判定** |
| < 0.4×中位 | 正常 | 只显示件数 |
| 0.4 ~ 0.9×中位 | 到复核点了 | 提示看一眼，给依据不给结论 |
| 0.9×中位 ~ 中位 | 建议换刀 | 该动手了 |
| ≥ 中位 | 必须换 | 红屏 |

### 顶部体检条：回答"到底在用真数据吗"

页面最上面那条灰底横条（`renderHB`）就是干这个的。它把 `/api/state` 的 `ingest` 字段直接摊开：

```
● 正在计算 | 源 T1111 @ 设备 4152 | 轮询 27 次 · 失败 0 | 最后拉到 15:45:58（滞后 58 秒） | 已封口 39 件 · 曲线 39 | 本把刀 冷启动（没人点过「已换新刀」）→ 件数只当下限 · 历史换刀 0 条（不足 5 条）
```

最后一段（`本把刀 …`）在 2026-10-21 搬到这里：原来它写在"模拟器控制"那块里，而那块在真实采集模式下现在**整块隐藏**（页面上不该出现"开始 / 1×3×10× / 重置 / 切到程序"这些假按钮），所以件数起算依据必须换个地方交代。

三种状态严格区分（这点很关键）：

| 显示 | 含义 |
|---|---|
| **正在计算**（绿） | `lag < 3 分钟`，数据在流 |
| **连接正常 · 暂无新数据（这把刀没在切削）**（黄） | 轮询在涨、`n_fail=0`，只是 T1111 没切削。9 把刀共用一条流，它只占 8.9% 时间，件数本来就不会一直涨 —— **不是故障** |
| **拉取异常**（红） | `n_fail > 0` 且 `lag > 3 分钟`，真出问题了 |

**信号只当"延长许可证"，不当触发器**：

- 到 0.4×M0 时看一次 HI（相对这把刀前 20 件的基线）是否已升 ≥1%
- 是 → 给许可，可以干到 0.9×M0
- 否 → 立刻按 0.4×M0 换

**信号算不出来、数据断了、几何定位失败 → 默认不给许可**。系统挂掉只会少赚，不会出事故。许可一旦判定就锁存在 `kv` 表，不会因为后面 HI 波动而反复横跳。

## 模拟器在演示什么（重点）

模拟器**自己会换刀，但不通知系统**。

页面底部那行"物理真值"（只在**模拟器模式**出现，influx 模式下连同整块"模拟器控制"一起隐藏）显示的是：这把刀实际用到第几件、真实寿命多少、已经发生过几次物理换刀。系统看不到这些——它只能靠员工点按钮。

所以你会看到：物理上换了 3 次刀，系统却认为"这把刀已经用了 246 件"，一路红屏。**这不是 bug，这是"换刀时刻在数据上不可观测"的直接后果**，也是为什么必须保留按钮。

实测四条自动路径全部失败（`../out_T1111/` 下有四份探查）：

| 路径 | 结果 |
|---|---|
| 人工台账 | 13/13 命中，但 9/23 起停更 |
| 件间空档 | 周期内中位 303s vs 跨周期 1051s，完全重叠，prec 0.01~0.14 |

### 拉取窗口怎么算（方案 A：水位线驱动）

```
W(k-1) = 上次实际拿到的最新 _time      -- 是数据的位置，不是 now
start  = min(W(k-1), now - 15s) - 5s
end    = now
若 now - W > 6h:  W = now - 6h         -- 停机太久，跳过无数据区
若 end - start > 6h: start = end - 6h
```

**为什么起点不能按系统时钟步进**（第一版的设计 bug，被用户抓出来）：

若 `end = T0+(k-1)×15`、`start = end-45`，起点由时钟决定。链路延迟 40 秒时，第 2 次在 10:42:00 查只能返回到 10:41:20；第 3 次窗口从 10:41:30 开始 —— **10:41:20~10:41:30 这段永久丢失**（第 2 次时还没入库，第 3 次起点已越过）。延迟越大，洞越宽。

改成让 W 追着数据走之后，延迟 40 秒窗口就自动变 45 秒，延迟 5 秒窗口就变 10 秒，`OVERLAP` 只要 5 秒保险。**失败时绝不动 W**，下一轮窗口自动变长补回来。

去重键是 `ts`（`raw_rows` 的 `UNIQUE`），窗口重叠的部分由 `INSERT OR IGNORE` 挡掉。

### 为什么在服务端 pivot

`L_tool_number` 是 **field 不是 tag**，直接 `filter` 返回 0 行。不 pivot 就得把全部刀的行拉下来再在客户端筛：实测 6 小时窗口 **21.4 万行，T1111 只占 721 行（0.34%）**，白传 99.7%。

改成：

```flux
|> pivot(rowKey: ["_time"], columnKey: ["nName"], valueColumn: "_value")
|> filter(fn: (r) => r.L_tool_number == "T1111")
```

1 小时 **1435 行、0.9 秒**。

### 实测到的三件事实（2026-10-21 12:20）

1. **`_time` 是 7 位小数（100ns）**，如 `2026-10-21T04:22:32.0866076Z`。Python 的 `%f` 只吃 1~6 位，直接 `strptime` 会 ValueError —— 第一版就栽在这，拉取线程每轮抛异常，水位线推不动、封口被跳过，`pieces` 一直是 0。现在 `parse_iso()` 统一截到微秒。
2. **`L_allnum` 是 9 把刀共用的全局计数器**。实时流里 T1111 的 allnum 从 61000 跳到 61143，差值 143，但其中只有 43 件是 T1111 的。所以件数必须数 `pieces` 的行数，**不能用 allnum 差值**。离线 CSV 是过滤后的单刀数据，差值恰好等于件数，这个坑以前不存在。
3. **设备 4152 现在跑的是 prog 17（`17(C5G25-03-AAR331)`）**，与离线标定用的 14/20/11 **不是同一个零件程序**。`history` 里没有 prog 17 的记录，M0 只能取经验值 100 件，页面会标红提示"M0 未标定"。真实上线需要为这个程序积累换刀记录。
