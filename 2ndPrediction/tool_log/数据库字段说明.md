# 数据库字段说明（`data/tool.db`）

> 对应代码：`server.py` / `server_stdlib.py`（建表）、`influx_source.py`（写 raw_rows）、`simulator.py`（件内处理）、`index.html`（读 `/api/state`）
> 实测样本：2026-10-21 16:46 的 `data/tool.db`（influx 模式，设备 4152 / T1111 / prog 17）
> 数据库类型：**SQLite 3，WAL 模式**，两个文件：`tool.db`（真实）与 `tool_sim.db`（演示），**不能混用**

---

## 0. 一句话理解这五张表

系统只有一条主线：**原始数据 → 一件一个数 → 一个寿命统计 → 一次人工确认**。

```
influx 采集流（9 把刀混流，只取 T1111）
        │  15 秒一批，INSERT OR IGNORE（靠 ts 去重）
        ▼
   ┌──────────┐   一件 = allnum 相同的 100~150 行
   │ raw_rows │   保留 7 天（按数据水位线滚动）
   └────┬─────┘
        │  封口：这件最后一行已过 120 秒 → 件内处理
        │  （裁 x 段 → Z 带 → 插值 40 点 → 负载门控 → 取中位）
        ▼
   ┌──────────┐   一件一行；load_med 就是"这件活干得多费劲"
   │  pieces  │   保留 30 天
   └────┬─────┘
        │  ÷ 前 20 件的中位 = HI（相对新刀的负载涨幅）
        │
        ├───────────────┐
        ▼               ▼
   ┌──────────┐   ┌──────────┐
   │ history  │   │tool_events│  ← 人点按钮产生；唯一能知道"换刀了"的来源
   │ 历史寿命 │   │ 操作台账 │     永久保留
   └──────────┘   └──────────┘
        │               │
        └──────┬────────┘
               ▼
          ┌────────┐
          │   kv   │  两个游标/锁存：封口进度、延长许可
          └────────┘
```

| 表 | 一行代表什么 | 谁写 | 谁读 | 保留 |
|---|---|---|---|---|
| `raw_rows` | 一个采样点（约 16ms 一个） | `InfluxPuller` → `write_rows()`；模拟器 `Simulator.step()` | `seal_pending_pieces()`、`compute_view()`（只数行数）、`cleanup()` | **滚动 7 天**，且至少留 5 万行 |
| `pieces` | 一件加工完成的工件 | 同上（封口时写入） | `current_prog()`、`compute_view()`、`cleanup()` | **滚动 30 天**，且至少留 300 件 |
| `tool_events` | 员工点的一次按钮 | `log_event()` | `compute_view()`（取最近 6 条 + 最近一次"换新刀"）、`undo_event()` | **永久** |
| `history` | 一把刀的实际寿命（件） | `init_db()` 灌种子、`log_event()`、`undo_event()` 删 | `compute_view()`（算 M0 / P85） | **永久** |
| `kv` | 一个需要跨重启活下来的游标或判断 | `kv_set()`、封口、`reset_all()` | `kv_get()` | **永久** |

> ⚠ 所有表都**没有 `tool_no` / `device_id` 字段** —— 全库是"单设备、单把刀"的假设。
> 因为 influx 查询里已经 `filter(L_tool_number=="T1111")`，进库的只有这一把刀的数据。
> **将来要同时收多把刀，`raw_rows` 必须加 `tool_no`，`pieces` 的主键必须从 `allnum` 改成 `(tool_no, allnum)`**，否则不同刀的同一件号会互相覆盖（`L_allnum` 是 9 把刀共用的全局计数器）。

## 1. `raw_rows` —— 原始采集层

**用途**：整个系统唯一"可回溯"的地方。所有指标都能从它重算，所以它必须尽量保持原样（不过滤 x 范围、不做归一化、不改数值）。
**写入节奏**：真实模式每 15 秒一批（一批十几到上百行）；模拟模式一件 60 行一次写入。

```sql
CREATE TABLE raw_rows(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT NOT NULL UNIQUE,
    allnum INTEGER, prog INTEGER,
    x_pos REAL, z_pos REAL, spindle_load REAL, spindle_speed REAL, feedrate REAL);
CREATE INDEX i_raw_allnum ON raw_rows(allnum);
CREATE INDEX i_raw_ts ON raw_rows(ts);
```

| 字段 | 类型 | 实测取值（真实库 6046 行） | 从哪来 | 有什么用 |
|---|---|---|---|---|
| `id` | INTEGER 自增主键 | 1 ~ 6046+ | SQLite | **① 保留策略的第二层保险**：`DELETE ... AND id < (最近第 50000 行的 id)`，保证再怎么样也不会把最近的数据删光；② 稳定排序兜底 |
| `ts` | TEXT，**UNIQUE** | `2026-10-21T05:34:51.864215Z`（UTC，27 字符定长） | influx `_time`（100ns → 截到微秒） | **这张表的命门，四个用途**：① 去重键（15 秒窗口有 5 秒重叠，同一行会被拉两次，靠 `INSERT OR IGNORE` + 本列 UNIQUE 挡掉）；② **水位线 W = MAX(ts)**，决定下一次查询从哪儿开始；③ 封口判据（这件最后一行是否已过 120 秒）；④ 7 天保留的比较基准（字符串字典序比较，所以**必须定长**） |
| `allnum` | INTEGER | 61167 ~ 61216（47 个不同值） | `L_allnum` | **"哪一件"的唯一标识**，`GROUP BY allnum` 就是"切件"。⚠ 这是**9 把刀共用的全局计数器**，实时流里它一次能跳 143，但其中只有 43 件是 T1111 的 —— **绝不能拿 allnum 差值当件数**，件数必须数 `pieces` 的行数 |
| `prog` | INTEGER | 全部 = 17 | `L_main_program` 开头数字（如 `17(C5G25-03-AAR331)` → 17） | 区分零件程序。M0（中位寿命）、历史寿命、换刀基准**全部按 prog 隔离**，因为不同程序寿命差很多（prog14≈89.5、prog20≈105.5）。解析不到时为 0 |
| `x_pos` | REAL | −1.0 ~ 289.47（切削段在 19~40） | `L_abso_x` | **几何对齐的主轴**。切断工序是 G96 恒线速，负载随 X 剧烈变化（纯几何，跟磨损无关），所以必须按 X 重采样才能把磨损那 2~3% 露出来。用途：① 裁出 `19~41` 的切削段（其余是 x≈238 快进/换刀位、x≈0 中心收尾）；② 插值到 19.0~40.0 / 40 点固定网格；③ Z 带选层的判据（选 x 跨度最大的那一层） |
| `z_pos` | REAL | −377.441（换刀位）/ −32.3（切断位）/ 189.361（快进位），100% 非空 | `L_abso_z` | **区分"X 相同但工步不同"**。`align_piece` 用它做 Z 带：把 z 排序、相邻差 >2mm 切层、选 **x 扫掠跨度最大**的一层（切断=Z 锁死+X 从 40 扫到 19）。⚠ 老库这列是 NULL（加列前入库），此时自动跳过 Z 带、退回旧口径 |
| `spindle_load` | REAL | 0 ~ 18777，均值 1664.9（**不是百分比，是原始负载值**） | `L_spindle_load` | **唯一的信号源**。磨损会让切削力上升 → 负载上升，但幅度只有 2~3%，所以必须靠"X 对齐 + Z 带 + 门控 + 中位"把它从工况波动里捞出来。0 表示空转/停机 |
| `spindle_speed` | REAL | 0 ~ 2002（应为 rpm，未经供应商确认） | `L_spindle_speed` | **当前不参与任何计算**。留作诊断：判断 G96 恒线速是否生效、这一行是否在空转、换程序后转速是否变了。将来做"转速归一化"或"恒转速筛选"时会用到 |
| `feedrate` | REAL | 恒 = 100.0 | **无来源，硬编码** | 真实采集流里没有进给 F 值字段（只有 `L_feed_override` 倍率），这个程序固定 F100，故按工艺值填。**只作占位，不参与计算**。要做进给归一化必须先拿到真实 F 或 override |

**索引为什么这么建**

- `ts` 上的 UNIQUE 自动索引 → 去重、水位线、保留策略全靠它，没有它 `INSERT OR IGNORE` 就是全表扫。
- `i_raw_allnum` → 封口时 `WHERE allnum=?` 反复查；`GROUP BY allnum` 也走它。
- `i_raw_ts` → `ORDER BY id`、`ts < cutoff` 的范围删。

**没入库但被用到的 influx 字段**

| influx `nName` | 用途 |
|---|---|
| `L_tool_number` | 只在服务端 Flux 里 `filter`，**不入库**（它是 field 不是 tag，不能直接 filter，必须先 `pivot`） |

**这张表的坑**

1. 一行的 `ts` 唯一，所以**同一次采样必须一行**。旧版模拟器一件 60 行共用一个 ts，加 UNIQUE 后只剩 1 行 —— 迁移代码里直接丢弃了那批旧数据。
2. `ts` 必须是**定长 27 字符**。混进 7 位小数（influx 原始精度）或 9 位会让字符串比较和保留策略全错，`parse_iso()` 会先规整到微秒。
3. 不要把 `spindle_load` 当百分比看，也不要拿它跟离线 CSV 的其他列混算 —— 单位没标定过（主轴负载表到底是扭矩% 还是功率%，供应商还没确认）。

## 2. `pieces` —— 件级汇总层（决策的唯一输入）

**用途**：把"一件 128 行原始数据"压缩成"一个数"。这是**粒度转换**，也是整个项目最关键的一步：原始行没有"件/寿命"语义、量级是几何的几百%，直接喂给判定层既算不动也毫无意义。

```sql
CREATE TABLE pieces(
    allnum INTEGER, prog INTEGER,
    load_med REAL, n_points INTEGER, ts TEXT, curve TEXT,
    PRIMARY KEY(allnum));
CREATE INDEX i_pieces_ts ON pieces(ts);
```

| 字段 | 类型 | 实测取值 | 怎么算出来 | 有什么用 |
|---|---|---|---|---|
| `allnum` | INTEGER **主键** | 61167 ~ 61215（45 件） | 来自 raw_rows 的件号 | **一件一行，"这是哪一件"**。⚠ 主键只有 allnum → 重复写入走 `INSERT OR REPLACE`（重新封口会覆盖）；⚠ 见 §0 末尾：多刀场景必须扩成 `(tool_no, allnum)` |
| `prog` | INTEGER | 全部 17 | 取该件第一行 `prog>0` 的值 | 把这一件归到哪个程序，从而对应哪一套 M0。取不到时是 0（这样的一件不会参与任何判定） |
| `load_med` | REAL | 1705.457 ~ 2067.895（45 件） | 40 点插值曲线 → 丢掉 <50% 中位的点 → 取中位 | **全村唯一的指标**。它代表"这一件加工时主轴负载有多高"。磨损 → 力↑ → 这个数往上爬约 2~3%；`HI = load_med ÷ 前 20 件中位` |
| `n_points` | INTEGER | 28 ~ 33（满分 40） | 门控后实际保留的点数 | **质量标记**：正常应是 30 上下；掉到 20 以下说明这一件缺行厉害（采样丢失/中途停机），这种件算出来的 `load_med` 不可信，是做数据质量监控的抓手 |
| `ts` | TEXT | `2026-10-21T05:35:23.355193Z` | 这件 raw_rows 里 `MAX(ts)`（UTC） | **这件干完的时刻**。用途：① `pieces ORDER BY allnum DESC LIMIT 1` 定"当前程序号"；② 30 天保留的比较基准；③ 前端逐件序列的时间轴 |
| `curve` | TEXT | 紧凑 JSON，375 ~ 384 字符，45/45 非空 | `grid = linspace(19, 40, 40)` 上的 40 个插值点，`round(...,4)` | **7 天之后唯一还活着的原始证据**。raw_rows 删了以后，靠它 + `median_from_curve()` 就能重算 load_med。**存的是"插值后、门控前"的原始值，不存 HI、不存归一化值** —— 归一化需要基线，而基线算法会变，存原始值才能在任何时点用新规则重算（比如门控阈值从 50% 改成 60%） |

**写入时机（封口，`seal_pending_pieces()`）**

两个条件**同时**满足才封：

1. `allnum < MAX(allnum)` —— 最后一件可能还在加工；
2. 该件最后一行距今 **> 120 秒**（`SEAL_DELAY_SEC`）—— 15 秒一批，一件的尾巴常跟下一批一起到。立刻封口会少几行 → 插值端点偏移 → `load_med` 偏低 → HI 往下跳一下。

进度游标存在 `kv.sealed_upto`；算不出 `load_med` 的件（行数不足、X 覆盖不够）**也会推进游标**，否则永远卡在同一件上。此时 `pieces` 里**没有这一行** —— 所以 `raw_rows` 的件数 ≠ `pieces` 的件数。

实测这一差额就是"诊断入口"（2026-10-21 的库：raw 47 件 → pieces 45 件）：

| allnum | 行数 | 情况 |
|---|---|---|
| 61213 | 8 | 正常一件 128 行，它只有 8 行 → 裁完 x 段不足 8 点 → 弃 |
| 61216 | 2 | `allnum = MAX(allnum)`，按规则不封口，还在等数据收齐 |

所以看到两者不一致**先别当 bug**，按上表逐件查是"废件"还是"还没封"。

## 3. `tool_events` —— 人工操作台账

**用途**：这是**系统唯一能知道"换刀了"的来源**。数据流里没有换刀指纹（`L_wear_no` 恒 11、`L_wear_x/z` 恒 0、`L_tool_number` 历史 CSV 里恒 T1111、`L_allnum` 换刀不重置），四条自动识别路径实测全堵，所以只能由人点按钮。

```sql
CREATE TABLE tool_events(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT, event TEXT, prog INTEGER, allnum INTEGER,
    pieces INTEGER, state TEXT, reason TEXT, limit_at INTEGER);
```

| 字段 | 类型 | 取值 | 有什么用 |
|---|---|---|---|
| `id` | INTEGER 自增 | — | ① 取"最近 6 条"（`ORDER BY id DESC LIMIT 6`）；② **撤销取 MAX(id)**，比按时间戳可靠（同一秒连点两次也不会错） |
| `ts` | TEXT | `2026-10-21 16:35:02`（**本地时间，空格分隔，**不是 UTC ISO**） | 人看的时间。⚠ 全库唯一的"异类"格式：`raw_rows`/`pieces`/`kv` 都是 UTC 定长 ISO，只有这张表是本地时间。前端靠 `slice(5,16)` 取 `10-21 16:35` 显示，所以能工作但**不要拿它和 raw_rows.ts 做比较** |
| `event` | TEXT | `new` / `hold` / `fail` | 三种操作：`new`=已换新刀（**重置件数基准**）、`hold`=继续加工（记下否决，不重置）、`fail`=刀废了（崩刀/超差，会问原因） |
| `prog` | INTEGER | 17 | 该事件归属的程序。换刀基准按 prog 隔离，一个程序换刀不影响另一个程序的计数 |
| `allnum` | INTEGER | 61215 等 | **点击那一刻的最新件号**。这是关键：下次 `compute_view()` 找 `event='new'` 的最近一条，把它的 `allnum` 当成 `base_allnum`，`used = COUNT(pieces WHERE allnum > base_allnum)` 就是"新刀干了几件" |
| `pieces` | INTEGER | 42 等 | 点击那刻"这把刀已用件数"。同时被写进 `history.life`（`new`/`fail` 时），所以它是**寿命标签的载体** |
| `state` | TEXT | `ok` / `chk` / `sug` / `bad` / `cnt` | 点击那一刻页面显示的四档状态。用途：事后复盘"他是在什么提示下决定换的"；也是校准判定线的依据（比如明明显示 ok 却换了 → 说明还有系统没看到的因素） |
| `reason` | TEXT | `崩刀` / `尺寸超差` / `工件表面差` / `其他` | 只有 `fail` 有值。崩刀 vs 正常磨钝是两回事，将来要分模型就先靠这个字段分层 |
| `limit_at` | INTEGER | 89 / null | 点击那一刻系统给出的换刀点（有许可时是 `0.9×M0`，否则是 `0.4×M0`）。用途：对比"实际件数"和"系统建议件数"，量化**系统建议偏保守还是偏激进** |

**这张表为空时会发生什么**：`used = COUNT(pieces WHERE allnum > min(allnum)-1)`，即库里该程序所有件都算作这一把 —— 页面显示 `≥N`（`base_src="cold"`），表示"至少这么多，不确定中间是否换过刀"。误差方向是**偏大 → 提前提示换刀 → 安全**。

**这张表与 `history` 必须同事务**：`new` / `fail` 一条事件会同时往 `history` 插一行寿命。2026-10-22 出过事故：异常在 `INSERT tool_events` 之后、`commit()` 之前抛出，结果就是**事件落了库、寿命没落库**（4 条事件对 0 条 history），而且那个悬空写事务把库锁住，拉取线程跟着报 `database is locked`。所以现在两件事在同一个事务里，异常统一走 `_rollback()`。

**判"漏点"依赖 `hmax`**：`suspect = used > max(1.3×hmax, hmax+20)`。当该程序历史不足 `MIN_N_BASIC` 条时 `hmax` 是 `None`（见 §4），此时**不做判断**，事件照记、`history.valid=1`，页面提示"历史只有 N 条，无法判漏点"。

## 4. `history` —— 历史寿命台账（M0 / P85 的唯一来源）

**用途**：给判定提供"这把刀一般能干多少件"。页面四个格子（最短 / 中位 / 常见上限 / 最长）和两条判定线（`0.4×M0` 复核点、`0.9×M0` 硬上限）全从这张表来。

```sql
CREATE TABLE history(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    prog INTEGER, life REAL, src TEXT, valid INTEGER DEFAULT 1);
```

| 字段 | 类型 | 实测 | 有什么用 |
|---|---|---|---|
| `id` | INTEGER 自增 | 1 ~ 16 | 撤销时删 `MAX(id)`（且 `src != 'seed'`），保证不会撤销到种子数据 |
| `prog` | INTEGER | 11 / 14 / 20 | 按程序隔离。**prog 17 目前 0 条 → M0 未标定 → 页面只给件数提示，不给换刀判断**（这就是为什么现在页面显示「—」） |
| `life` | REAL | 47 ~ 197 件 | **这一把刀实际干了多少件**。由 `new`/`fail` 事件时页面上的 `used` 写入。中位数 = `M0`，85 分位 = `P85`（常见上限） |
| `src` | TEXT | 全为 `seed`（真实台账还没产生） | 来源标记：`seed`=程序首次启动灌的初始台账（prog11 3 条 / prog14 7 条 / prog20 6 条，共 16 条）；`new`/`fail`=人工确认的。用途：① 撤销时排除种子；② 区分"人工判断的正常换刀"和"真实失效"，将来算失效成本 ρ 时要分开 |
| `valid` | INTEGER | 全为 1 | **数据质量闸门**。`1`=计入统计，`0`=疑似漏点（"记了但不计入基准"）。判据：`used > max(1.3×历史最长, 历史最长+20)`。实测教训：漏点一次就出现 501 件的"寿命"，P85 从 108.8 飙到 192.1，一次忘点永久带偏基准。⚠ **该程序历史 < 3 条时 `hmax=None`，判据无从计算 → 一律记 `valid=1`**（不能因为判不了就丢数据，也不能拿经验值 100 去卡） |

**样本门槛（代码里的，不在表里，但决定这张表怎么被读）**

| 门槛 | 值 | 不足时 |
|---|---|---|
| `MIN_N_BASIC` | 3 | 最短/中位/最长 全部返回 `None`，页面显示「—」 |
| `MIN_N_P85` | 5 | `P85` 与两条判定线不可用 → `judge_ok=False` → 状态降为 `cnt`（只报件数） |

理由：只有 1 条记录时 `最短=中位=P85=最长`，四个数字一样，看着确凿其实等于没说 —— 项目里真出现过页面四格全显示 100 的事故（兜底值被当成计算结果）。

## 5. `kv` —— 游标与小状态

**用途**：需要跨重启活下来的少量零碎状态。不用单列表是因为这些值必须和主数据在同一个事务/同一个文件里，重启后不会丢。

```sql
CREATE TABLE kv(k TEXT PRIMARY KEY, v TEXT);   -- v 一律存字符串
```

**当前实际存在的键（真实库）**

| `k` | `v` 实测 | 写入方 | 作用 |
|---|---|---|---|
| `sealed_upto` | `61215` | `seal_pending_pieces()` | **封口进度游标**：已经处理到哪一件。没有它时取 `MIN(allnum)-1`（相当于从头封）。有了它，重启后不会重复处理 47 件旧数据 |
| `grant_{prog}_{base_allnum}` | `grant_17_61166 = "0"` | `compute_view()` | **延长许可的锁存**：`"1"`=给了延长许可（可干到 `0.9×M0`），`"0"`=信号没确认（到 `0.4×M0` 就换）。键里带 `base_allnum` 是为了"换一把刀重新判断"，旧锁存自动失效。⚠ 注意 `61166 = 61167 − 1`（库里最小件号减 1）→ 说明这条是**冷启动**时写的（当时没人点过「已换新刀」） |

**关键设计：许可一旦判定就锁存，不再重算。** 否则 HI 在 1% 门槛附近抖动会导致换刀点反复横跳。另外**样本不足时绝不写这个键**（`judge_ok=False` 直接跳过），否则等以后样本够了还会沿用当时那个没依据的判断。

`reset_all()` 会清空整张 `kv`（连 `sealed_upto` 一起），所以重置后重新封口一遍。

## 7. 常用查询（排查/运维）

```sql
-- 库有多大、数据到哪儿了（水位线）
SELECT (SELECT COUNT(*) FROM raw_rows) raw_n,
       (SELECT MAX(ts) FROM raw_rows) raw_w,
       (SELECT COUNT(*) FROM pieces) piece_n,
       (SELECT COUNT(DISTINCT allnum) FROM raw_rows) raw_piece_n;

-- 被丢弃的件（raw 有、pieces 没有）—— 数据质量问题
SELECT DISTINCT r.allnum, COUNT(*) rows
FROM raw_rows r LEFT JOIN pieces p ON p.allnum=r.allnum
WHERE p.allnum IS NULL GROUP BY r.allnum ORDER BY r.allnum;

-- 一件的行数分布：掉到 20 以下的要查是不是中途停机/采样丢包
SELECT allnum, COUNT(*) n FROM raw_rows GROUP BY allnum ORDER BY n ASC LIMIT 20;

-- 当前这把刀用的是哪条基准（没有记录 = 冷启动）
SELECT id,ts,event,allnum,pieces,state,limit_at
FROM tool_events WHERE event='new' AND prog=17 ORDER BY id DESC LIMIT 1;

-- 同程序历史寿命 → 手算 M0 / P85
SELECT prog, COUNT(*) n, MIN(life), MAX(life) FROM history
WHERE COALESCE(valid,1)=1 GROUP BY prog;

-- 曲线是否还在（0 表示全是加列前的老件，无法重算）
SELECT COUNT(*) total, SUM(curve IS NOT NULL) with_curve FROM pieces;

-- 封口游标 vs 最新件号（差很多 = 卡住了）
SELECT (SELECT v FROM kv WHERE k='sealed_upto') sealed,
       (SELECT MAX(allnum) FROM raw_rows) latest;
```

## 8. 铁律（改代码前必读）

1. **件数只能数 `pieces` 的行数**，不能用 `MAX(allnum)-MIN(allnum)+1`。`L_allnum` 是 9 把刀共用的全局计数器，实时流里差 143 只有 43 件是本刀的。离线 CSV 是过滤后的，所以当年没暴露。
2. **保留策略不能用系统时钟**。`cutoff = now - 7d` 在放假 10 天后会把库删空。必须用数据水位线 `W = MAX(ts)`，`cutoff = W - 7d`。第二层保险：`id < 最近第 50000 行的 id` 同时成立才删。
3. **`ts` 必须定长 UTC**。`raw_rows` 存 27 字符 ISO；`tool_events` 存本地时间 `YYYY-MM-DD HH:MM:SS`，两者**不可比较**。
4. **不要手工改 `history`**。它是 M0 的唯一依据，改一条就把判定线整体挪了；要纠正走页面「撤销上一次」（会同时删 `tool_events` 和 `history` 的最大 id）。
5. **不要删 `-wal` / `-shm` 文件**。它们是 WAL 模式的正常产物，单独删会丢最近未合并的数据；要收缩用 `PRAGMA wal_checkpoint(TRUNCATE)`（服务退出时自动做一次）。
6. **两个库不能混用**。`tool.db` 真实、`tool_sim.db` 演示。曾因共用一库让模拟器 29 件假数据灌进真实库，且因为还在 7 天保留期内，清理策略根本不会删。
7. **老库补列顺序**：`raw_rows` 若缺 UNIQUE 需要重建，补 `z_pos` 的 `ALTER TABLE` 必须在重建**之后**（重建脚本本身已含该列，先补等于白做）。
8. **写事务绝不能让异常穿过去**（2026-10-22 血案）。SQLite 的事务挂在**连接**上：一次没 `commit()` 也没 `rollback()` 的写会一直悬着占住写锁，症状出现在**别的线程**（拉取线程 `database is locked`），而且那个悬空事务还可能被同一连接后面某次 `commit` 顺手带上 → 出现"事件落了库、寿命没落库"这种半截数据。所有写路径统一 `try: ... commit() except: _rollback(); raise`。

## 9. 两个版本的服务对库的影响

| | `server.py`（FastAPI） | `server_stdlib.py`（零依赖） |
|---|---|---|
| 数据源 | `sim` / `influx` 可选 | **只有 sim**（`/api/state` 里 `source="sim"`、`ingest=null`） |
| 保留策略 | 有（`Janitor` 线程，每小时一次） | **没有** —— 表只增不删，库会一直长 |
| 建表 / 判定口径 | 见上文 | **完全一致**（DDL、门槛、参数都对齐，否则页面结论会不一样） |

生产上机用 `server.py`；厂里装不了第三方包时才退到 `server_stdlib.py`，但那时得自己安排清理（否则 7 天后库仍不缩，只是不删数据 —— 不影响正确性，只影响磁盘）。
