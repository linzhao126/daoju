## 一、四格统计：结论正确，但页面此刻没有数据

### 数据来源

```sql
SELECT life FROM history WHERE prog=? AND COALESCE(valid,1)=1 ORDER BY id
```

（`server.py:557-559`）

`history.life` = 一把刀从"已换新刀"到"刀废了/换刀"之间用掉的件数。  
**它来自员工点按钮时记下的件数，不是从机床信号反推的**——这是架构反转（发令换刀）的必然结果，冷启动必然是 0 条。

### 四个值怎么算

| 页面显示    | 实际计算                      | 最低样本 | 代码位置            |
| ------- | ------------------------- | ---- | --------------- |
| 同程序最短   | `min(hist)`               | ≥3 条 | `server.py:568` |
| 同程序中位   | `median(hist)` → 即 **M0** | ≥3 条 | `server.py:570` |
| 同程序常见上限 | `percentile(hist, 85)`    | ≥5 条 | `server.py:572` |
| 历史最长    | `max(hist)`               | ≥3 条 | `server.py:569` |

门槛常量：`MIN_N_BASIC = 3`、`MIN_N_P85 = 5`（`server.py:80-81`）。  
P85 门槛更高的原因写在注释里：n=7 时 P85 的 bootstrap 区间是 [85,197]，跨度 103%，等于没定。

### 为什么现在全是「—」

- 四格统计的是"同程序历史换刀记录"，**和当前这把刀无关，换刀不改变它们**（`server.py:553` 注释）。
- 样本不足时 `hmin / m0 / p85 / hmax` 全部返回 `None`，页面画「—」，并显示"需 ≥3 条历史 / 需 ≥5 条历史"。
- 这是 **2026-10-21 修出来的有意行为**：原来无历史时 `hist=[100.0]`，导致 median=p85=min=max=100，页面四个一模一样的"确凿数字"，用户误以为系统算出了四个值（`server.py:554-556`）。

> 你截图里四个「—」+ 顶部"历史换刀 0 条（不足 5 条）"= 系统正常工作，不是故障。

## 二、经验值 100：跟四格没有任何计算关系

```python
EXP_M0 = 100.0   # 无历史时的"经验提示值"，只作提示线，不参与任何判定
```

（`server.py:83`）

- 它是**硬编码常量**，不是由四格算出来的。
- 真实 M0 只在 `n_real >= 5` 时由中位数得出；样本不够时 `m0 = None`，页面才退回显示这个 100。
- 页面措辞刻意写成「暂以经验值 **100** 件作提示线（**不是判定依据**）→ 只按件数提醒，不判断该不该换」（`index.html:317-318`），就是为了防止误解。
- 100 的**来源**是离线实测：prog14 的 M0 = 89.5（n=6, CV 32.3%）、prog20 的 M0 = 105.5（n=6, CV 4.5%）、合并 99 → 取整 100。但在代码里它就是个常量，没有任何运行时计算过程。

## 三、进度条：数字对，公式和变色机制都需要纠正

### 3.1 蓝色条长度怎么来的

```js
const span = (hasM0 && p85 !== null) ? Math.max(m0 * 1.15, p85 * 1.2)
         : Math.max(used * 1.25, d.exp_m0 || 100);
$("fill").style.width = Math.min(100, used / span * 100) + "%";
```

（`index.html:343-345`）

- **分母是"画轴跨度 span"，不是经验值、也不是 M0。**
- 当前无历史：`span = max(55×1.25, 100) = 100` → `55/100 = 55%`。  
  **这个 55% 纯属巧合地等于 55÷100**，换一个件数就不再对应。
- 有历史后：`span = max(m0×1.15, p85×1.2)`，分母整体换人 → **同一件数对应的条长会变化**。  
  所以不能把条长当作"进度百分比"来读，它只在同一次渲染内部有相对意义。

### 3.2 变色不是百分比阈值，是五档状态

颜色由 `state` 决定（`index.html:311`），`state` 由件数与判定线比较得出（`server.py:615-626`）：

| 状态    | 颜色           | 显示文案           | 触发条件                        |
| ----- | ------------ | -------------- | --------------------------- |
| `cnt` | 蓝 `#185FA5`  | 件数提示 · 暂不做换刀判定 | `judge_ok = False`（历史 <5 条） |
| `ok`  | 绿 `#0F6E56`  | 状态正常           | `used < b`                  |
| `chk` | 棕 `#854F0B`  | 到复核点了          | `used ≥ b`                  |
| `sug` | 橙红 `#993C1D` | 建议换刀           | `used ≥ h`                  |
| `bad` | 红 `#A32D2D`  | 已过中位寿命，必须换     | `used ≥ m0`                 |

判定线：

```python
BASE_F, EXT_F = 0.4, 0.9                     # server.py:73
b = ceil(BASE_F * m0)  # 复核点 = 0.4 × M0
h = ceil(EXT_F * m0)   # 建议换 = 0.9 × M0
m0                     # 必须换 = 1.0 × M0
```

### 3.3 三个必须记住的推论

1. **变红的充要条件 = `used ≥ M0` 且 `n_hist ≥ 5`。** 不存在"条走到 80% 就红"这种规则。
2. **条没满就红是设计如此。** 因为 `span ≥ m0×1.15` 留了余量，红色通常出现在条走到 **60%~87%** 之间（取决于 P85/M0 比例）。
3. **当前页面 `state = cnt`，永远不会变色。** 加工到 55 件还是 500 件，都是同一条蓝条。

> 该盯的指标是 `used` 与 M0 的差值，不是条长的百分比。

## 五、等攒够 5 条历史后，页面会怎么变

| 项         | 现在                    | n ≥ 5 之后                                  |
| --------- | --------------------- | ----------------------------------------- |
| 四格        | 全「—」                  | 四个真实数字，`gMaxN` 显示"最长 X · N 把"             |
| 顶部状态药丸    | 蓝 · 件数提示              | 绿/棕/橙红/红 四档之一                             |
| 条的分母      | `max(used×1.25, 100)` | `max(m0×1.15, p85×1.2)`                   |
| 判定线 b / h | `None`                | `⌈0.4×M0⌉` / `⌈0.9×M0⌉`                   |
| 延长许可      | 不给，且不写 `kv`           | 跨过 b 时评估一次 HI 升幅 ≥1%（`TAU`）→ 锁存 h，否则按 b 换 |
| 信号行       | "M0 未标定，仅供参考"         | "已获延长许可" / "信号未确认，按基准换"                   |
